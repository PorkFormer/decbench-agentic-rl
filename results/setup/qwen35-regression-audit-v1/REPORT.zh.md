# Qwen3.5 Agentic RL 退化审查

审查日期：2026-11-02。对象：作业 3807371 / attempt-6，Qwen3.5-4B，
AgentEvolver HET actor、GRPO outcome advantage、byte-match-v8-proxy-v1。

本次确认的是工具动作协议退化：后测无法写出待评分代码。不能由零奖励直接推断
反编译语义能力全部丧失。训练和恢复确实执行成功，但质量验收失败。

## 发现一：终局奖励连带强化非法动作

当前环境每一步返回 reward=0，最终只评分文件。GRPO 用同一个组内标准化终局优势
覆盖轨迹中的所有有效 loss token：
`.tools/AgentEvolver-qwen35/agentevolver/module/trainer/ae_ray_trainer.py:215`。
工具报错本身没有单独的负奖励；一次成功写入后，后续非法动作不必降低最终文件得分。

根据已保存的 160 条训练轨迹重建，40 个任务组均有 4 条 rollout：

- 54 条轨迹得到正优势；其中 48 条包含仍进入 loss 的非法动作。
- 正优势轨迹保留约 82,311 个 loss token，其中约 36,491 个来自非法动作，约占 44.3%。
- 具体例子：`rollouts/traj_10.jsonl` 的第 2 条轨迹，任务
  `6f14ff55cb692b5d3e8269c6`，终局奖励 1.0、正优势。12 次动作中只有第一次
  decompile 和第八次 Write 合法，其余 10 次非法动作也被正优势覆盖。

这说明“文件最终得分较高”与“整段交互都值得加强”并不一致。它是本次配置的
明确风险，不等于 GRPO 算法实现错误。负优势轨迹也会抑制非法动作；仅凭上述正向
计数，不能计算最终净梯度方向，也不能证明它单独导致了全部退化。

## 发现二：训练截断与多轮交互预算不一致

`configs/agentevolver/qwen35.yaml:13` 将 prompt/response 配成 12,288/4,096。
`cmt_linear.py:601` 从第一条 assistant 消息开始划分 response，后续工具观察也算在
response 长度内。`agentevolver/schema/trajectory.py:101` 只保留前 4,096 token。
交互本身却允许 16K 总上下文、最多 12 次动作。

所以“单轮最多生成 4,096 token”和“整段多轮轨迹最多训练 4,096 token”被放到了
同一个长度配置上。工具观察虽不参与 loss，仍会占用预算、挤掉后续写代码和修复动作。

保存文本回放统计：

- 52/160 条轨迹被截断，占 32.5%。
- 372 次可解析 Write/Edit 中，47 次完全未进入 loss，13 次只有部分 token 留下。
- 完整轨迹约 391,546 个 loss token，截断后保留约 248,671 个，丢失约 36.5%。
- 有 2 条正奖励、正优势轨迹没有任何 Write/Edit token 保留，却仍用最终文件奖励
  更新其前面的动作；对应 step 2/index 8 与 step 10/index 12（index 从 0 开始）。

这是需要优先修复的训练输入问题。它能够削弱正确产物与奖励的对应关系，但目前没有
修复后的对照实验，不能量化它对本次格式崩溃的独立贡献。

这些批次的任务不同，不是逐步固定验证，不能把比例差异全归于参数更新。
但训练侧本身也出现了协议失败加重，问题并不限于最终验证的 32 个任务。
第 10 批 rollout 在第 10 次更新之前采样，不能当成 step-10 checkpoint 的验证。

训练采样温度为 0.8；固定验证为温度 0、每任务一次。随机采样偶尔能恢复合法 Write，
而贪心生成可能持续选择说明文字。这是训练仍有部分非零奖励而后测全零的一种合理解释，
尚未通过同一 checkpoint 的采样对照验证。

当前只在 step 0/10 做固定验证，中间未设置动作合法率、成功写出率的停止门槛。
`training_verified=true` 验证的是执行和恢复，`validation_improved=false` 已明确
记录效果失败。以后应将“执行验收”与“模型可用性验收”分别作为运行结果展示。

## 已核查、尚不能认定为根因的项目

- 调度作业 3807371 为 COMPLETED/0:0；每 rank 10 次真实更新、有限梯度、参数抽样变化，
  step 5 新进程恢复后继续更新均有记录。本次没有环境基础设施失败记录。
- 30/40 个组有奖励差异，188,128/248,659 个实际 loss token 的优势非零。
  因此不能解释成“完全没有奖励信号”。
- 在保存文本重建中，160/160 条轨迹的增量 token 拼接与完整聊天模板一致。
  154/160 条截断后解码文本与保存的训练输出完全匹配；其余存在差异。
  重建保留 token 总数比运行记录多 12。原始生成 token ID 未持久化，故这不是
  对运行时原始 token 的逐位验证，不能宣称彻底排除了模板/token 问题。
- 审查涉及的 9 个训练配置/源码文件均与该 run 的 training.lock.json 匹配，见
  `source-check.json`。环境适配器不在这份训练锁内，未将其冒充为该锁验证通过。
- 学习率、KL 系数、HET 路径和恢复分界都值得作为对照变量；当前没有证据把其中
  任意一项单独判定为根因。PPO clipfrac≈0 是单次更新前计算时可能出现的正常现象，
  不证明更新后策略没有漂移。日志中 lr 显示 0.000 也不能覆盖配置中的 1e-6。
- pilot 冻结集为 108 train / 32 validation；本轮仅实际采样 40 个唯一训练任务、
  160 条 rollout。10 步是闭环验收，不能代表全量语料已经充分训练。

## 建议的修复与验收顺序

1. 修复多轮训练预算：区分单次生成上限与整段轨迹上限；保留完整动作与对应观察，
   或使用经验证的按动作切片方法。遇到超长应明确处理，不能只保留轨迹前缀却继续
   当作完整轨迹训练。检查奖励对应的 Write/Edit 是否实际进入 loss。
2. 修复协议稳定性：明确单个 JSON 输出契约、提供可理解的格式错误反馈；可对比
   schema 约束生成。变更必须同时应用于基线与训练后模型、冻结新评估版本，保留本次结果。
3. 针对错误信用分配做消融：考虑有限的非法动作惩罚、完成后的无效循环处理，或
   按可验证状态进步定义过程奖励。不要用调用次数作正奖励，也不要把放宽解析规则
   后的分数冒充模型学习提升。
4. 从原始基线权重做短程对照，在 step 1/2/5 固定验证，分别记录 JSON 合法率、
   写出率、可编译率、byte-match、组内差异和 KL，并设置停止条件。
   step-10 checkpoint 保留为失败对照，不直接延长它的训练。

本次只完成审查、重建统计和报告；没有更改训练行为、奖励或解析器，没有启动新的 GPU 训练。
